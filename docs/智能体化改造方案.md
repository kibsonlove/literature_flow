# 智能体化改造方案

> 状态：**P0–P2 已实施**（2026-10-01），P3 待定。本文档由《智能体化改造调研》升级而来，调研结论已并入。
> 配套：《项目架构与开发指南.md》讲现有代码结构；《交接文档.md》讲当前进度与接手指引。
> 实施结果与本文档的差异见文末 **第 5 节「实施记录」**。

## 0. 已拍板的决策

| 决策点 | 结论 |
|---|---|
| LLM 通道 | **网页端 webchat 为默认**（零 API 费），设置里可留 API 备选项 |
| 编排形态 | **粗粒度规划**：开头一次出计划，确定性代码执行，失败才回问 LLM（每次任务 2-4 次 webchat 调用） |
| 首发形态 | **交互式（网页面板）优先**，自动化/定时为后续阶段 |
| 并行 | 不做并行，webchat 同一浏览器 profile，任务**只能串行** |
| 写库闸口 | 写库步骤一律暂停等用户确认，agent 无静默写权限 |

## 1. 总体架构

```
用户（自然语言下指令）
        │
┌───────▼────────┐
│ 对话面板（前端） │  计划卡片 / 危险步骤红色高亮 / 逐步日志 / 总结
└───────┬────────┘
        │ /api/agent/plan | confirm | status
┌───────▼──────────────┐     ┌──────────────────────┐
│ agent_orchestrator   │────▶│ WebChat（大脑，零费）  │
│ 计划→执行→观察→回炉   │     └──────────────────────┘
└───────┬──────────────┘
        │ 统一调用
┌───────▼──────────────┐
│ agent_tools 注册表    │  名称/参数/描述/只读或写库(danger)
└───────┬──────────────┘
        │ 复用现有能力（不重写）
│ litsearch / zotero_io / kb / batch / tools / …
```

执行循环（形态 C 混合）：
1. 用户输入任务 → orchestrator 调一次 webchat，产出 JSON 计划（步骤列表，每步引用一个注册工具）；
2. 逐步执行：只读步骤直接跑；`danger=True` 步骤挂起，等用户在面板上确认；
3. 步骤失败或结果明显异常 → 才回问 LLM（最多 2 次），仍失败则中止并汇报；
4. 全部完成 → 调一次 webchat 生成总结（改了什么、有哪些挂起未确认）。

## 2. 分阶段实施

### P0 工具注册表（地基，半天）
- 新建 `webapp/core/agent_tools.py`：`TOOLS` 列表，每项含
  `name / description / params(schema 说明) / danger(bool) / fn`。
- 首批注册 8 类：文献检索、检索式生成、结果入库（danger）、条目/分类查询、
  知识库语义检索、维护工具箱（变更类默认 dry-run，danger）、报告产物读取、精读状态查询。
- **纯新增文件，不改现有模块**，零风险。验收：注册表能导出一份"给 LLM 看的工具说明书"文本。

### P1 计划-执行编排（核心，1-2 天）
- 新建 `webapp/core/agent_orchestrator.py`：计划 prompt（含工具说明书 + 研究课题 + 输出 JSON 约束）、
  执行器（步骤状态机：`pending / awaiting_confirm / running / done / failed / skipped`）、
  失败回问逻辑、任务状态落 `webapp/cache/agent_tasks/`（可再生目录，支持中断续跑）。
- 新增 3 个路由：`POST /api/agent/plan`（生成计划并返回待确认）、
  `POST /api/agent/confirm`（放行某个 danger 步骤）、`GET /api/agent/status`（日志与进度）。
- 计划 prompt 必须走 `def` 同步路由（同 `gen_queries` 的先例，Playwright 不能进事件循环）。
- **测试红线**：只读任务可实测；写库任务用小样 + 当场同意可整删的测试分类，跑完清理并列清单。

### P2 对话面板（1 天）
- 前端新增「智能体」面板：输入框 → 计划卡片（danger 步骤用 `.danger` 红色高亮 + 确认按钮）→
  逐步日志流 → 总结。样式遵守全站约定（悬停不改背景色、muted 用 `#6b6b6b`）。
- 界面文案写明：任务串行执行、批量精读一次任务最多一个。

### P3 自动化形态（可选，后做）
- 复用同一注册表与编排器，加定时触发（如每日订阅追踪）。
- 无人值守时 danger 步骤**不执行**，挂起攒成待确认清单，用户下次打开面板一键审批。

### 明确不做
- LangGraph 等 Agent 框架重构（依赖重、与 webchat 不兼容，收益低）；
- 多任务并行；agent 静默写库；逐步决策紧循环（webchat 开销不可承受）。

## 3. 硬约束（实施全程有效）

1. LLM 默认走网页端 webchat；API 仅作显式备选。
2. 写库动作（入库、移动分类、删除、批量精读写笔记）必须人工确认；变更类默认 dry-run。
3. 绝不拿用户真实文献做端到端测试。
4. 通用化：命名/界面文案不绑定领域；路径一律 `config` 函数读取，禁硬编码。
5. webchat 浏览器 profile、任务缓存等临时产物按现有约定及时清理。
6. 已有笔记不重复生成；入库查重（DOI+标题指纹）逻辑复用，不绕过。

## 4. 风险与对策

| 风险 | 对策 |
|---|---|
| webchat 页面改版导致大脑失联 | 失败明确报错（不静默），复用 `WebChatError` 体系与挂载检测经验 |
| LLM 产出的计划 JSON 不合规 | prompt 里给 few-shot + 严格 schema 校验，不合规直接回问一次重出 |
| 计划执行到一半用户关页面 | 状态落盘 `agent_tasks/`，重开后可续跑 |
| 危险步骤被误确认 | 确认按钮只针对单步骤，且面板展示该步骤影响的条目数 |

## 5. 实施记录（2026-10-01）

P0 / P1 / P2 已按本方案落地，前端 UI 一并重做。落地结果与本文档第 1–2 节的差异如下。

### 5.1 实际产出

| 层 | 文件 | 说明 |
|---|---|---|
| 工具注册表 | `webapp/core/agent_tools.py` | 14 个工具，覆盖方案提到的 8 类能力；`danger` 支持**三态**（只读 / 视参数而定 / 一定写库） |
| 编排器 | `webapp/core/agent_orchestrator.py` | 计划 prompt（含 `few-shot` + 严格 schema 校验）、`pending/awaiting_confirm/running/done/failed/skipped` 状态机、失败回炉（≤2 次）、状态落盘、总结 |
| 路由 | `webapp/app.py` 末尾 | `plan / run / confirm / skip / abort / delete / status / tools` 共 8 个 |
| 前端 | `static/agent.js` + `templates/index.html` + `static/style.css` | 侧栏导航 + 智能体指挥台 + 全局「大脑」开关；样式表整体重做 |

### 5.2 相对方案的调整（都是实施中发现的必要项）

1. **路由从 3 个增到 8 个**：除 `plan / confirm / status` 外，补了 `run`（开始/继续执行）、`skip`（跳过某步）、`abort`（中止）、`delete`（删任务）、`tools`（工具清单给前端渲染）。只有 `plan` 无法表达"计划已出、等用户点开始"。
2. **一律后台线程 + 轮询**：LLM 调用要开浏览器（30 秒+），同步返回会把请求挂死。路由立刻返回任务号，前端轮询 `status`。同时用 `_AGENT` 闸门强制**任务串行**。
3. **执行期间不持任务锁**：最初按"任务锁包住整个 `advance()`"实现，结果前端轮询全部被堵死（测试时表现为"页面像卡死"）。改为 `_RUNNING` 集合做互斥、文件读写各走短锁。
4. **Windows 文件并发坑**：边写任务文件、边被前端轮询读取时，`os.replace` 会报 `WinError 5 拒绝访问`，导致执行中途崩掉。已改成"重试 + 兜底原地覆写"，并在 `delete_task` 里避开 `os.path.isfile` 的瞬时误判。
5. **步骤间数据传递**：新增 `$sN.字段` 引用语法（`$s2.results`），列表可投影（`$s1.items.key` 把每个元素的 `key` 抽成字符串列表）。引用取不到就**明确报错**，不静默传 `None`。
6. **写库工具用「探活」兜底**：Zotero 没开时本地读接口会静默返回空，会让模型误判"库里没有"。工具层统一先 `ping()`，未检测到 Zotero 就明确报错。
7. **危险步骤的影响面在挂起时才算**：`lit_import` 的 `records` 常是 `$sN.results` 引用，计划阶段拿不到条数；因此改为**挂起瞬间解析参数**再算影响面，确认界面显示的数字才准确。
8. **精读纳入可调度范围**（方案里"P1 先不纳入、P2 再放开"）：已提供 `reading_candidates` + `batch_notes`，并在编排器里加了"一次任务最多一个批量精读"的保护。
9. **UI 一并重做**：由「顶栏按钮 + 居中弹窗」改为「左侧栏导航 + 主工作区」，智能体作为默认视图；原各功能面板保留为浮层。**所有既有元素 ID 原样保留**（`app.js` 依赖约 170 个 ID）。全站按钮悬停仍只压暗、不改背景色。
10. **顺带修掉旧待办**：原 `390px` 下 `.topbar-actions` 不换行导致的页面级横向溢出，随侧栏布局一并解决（实测 1440 / 1024 / 390 三档 `scrollWidth == clientWidth`）。

### 5.3 边界（与方案一致，未放宽）

- 写库动作一律 `danger`，挂起等用户点确认；变更类维护脚本默认 dry-run。
- 无多任务并行；无 agent 静默写库；无逐步决策紧循环。
- LLM 默认网页端；测试不用 API 通道（会花钱）。

### 5.4 首轮使用反馈的修复（2026-10-01 晚）

用户试用后提了两条，都是真问题：

1. **计划出来后改不了** → 新增**单步改参数**：计划卡片里每个还没执行的步骤都有「改参数 / 跳过这步」。
   参数表单按工具 schema 生成（字符串 / 数字 / 勾选 / 多行列表）；值形如 `$s2.results` 的**引用型参数只读展示**，
   因为它本来就该由上一步自动带入。后端新增 `POST /api/agent/update`，只允许改 `pending` / `awaiting_confirm` 的步骤。
   另加 `POST /api/agent/replan`：对当前任务**按原任务文本整份重排**，不必重新输入。
2. **中止后按钮没了、既不能续跑也不能重来** → 根因是 `abort()` 把 pending 步骤全标成了 skipped。
   改为**保留未执行步骤**，任务置 `aborted`，卡片与顶部都给「继续执行」；真正的停止靠 `_ABORT_FLAG`
   与后台线程协作（每轮循环开头检查一次），当前正在跑的那一步会跑完后退回 pending 并注明"未确认是否完成"。

顺带收紧了三条安全语义（都是实现这一条时想到的，属于"不做会出事"）：
- **改了写库步骤的参数 → 上一次的「确认」作废**（`approved=False`，退回待确认）。否则"换了入库分类却沿用旧确认"，
  等于用户确认的是另一件事。
- **影响面不许缩水**：引用解析不到时，确认界面必须写"实际影响面可能更大"，不能按空参数算成一个假数字。
- **在计划上点「跳过」不会把任务带跑起来**：只有任务本就在执行中（running / awaiting_confirm）才"跳过并继续"。

### 5.5 计划质量：引用归一 + 计划体检（2026-10-01 晚，追问「这个参数是什么意思」时发现）

用户问 `records` 是什么意思，顺带查出**模型产的引用经常是坏的**。实测那条真实任务：

```json
{"tool": "lit_search",  "args": {"queries": []}}                      ← 该引用上一步却留空
{"tool": "lit_import",  "args": {"records": " s2.results"}}           ← 漏掉开头的 $
```

后果：引用不被识别 → 参数当普通字符串传进工具 → 那一步必然失败，而且用户是**点了执行才发现**。

三层修法：

1. **引用归一**（`_fix_refs()`）：把 `s2.results`、`$ s2.results`、`$s2.results` 统一成 `$s2.results`；
   在 `_normalize_steps()`（计划落盘时）与 `update_steps()`（用户手改时）都跑一遍。
2. **说明书补输出字段**（`agent_tools.RETURNS` / `RETURN_FIELDS`）：每个工具列出自己的输出字段，
   写进给 LLM 的说明书——模型得先知道上一步有什么字段可引用，才不会瞎写。
3. **计划体检 + 回问一次**（`_plan_issues()`）：落盘前检查 ① 必填参数为空 ② 引用指向不存在/
   更靠后的步骤 ③ 引用的字段不在该工具的输出清单里。有问题就**带着问题回问 LLM 一次**（方案原本
   就承诺"不合规直接回问一次"）；仍不通过**不失败**，而是给该步骤挂 `warning`，前端用黄色条提示
   "建议点「改参数」补上再执行"——把决定权交回用户，而不是替他把任务毙掉。

另外两处配套：
- 执行侧的 `_resolve_refs()` 也容忍漏写 `$` 的写法（要求带点，避免把普通字面量误判成引用），
  这样拿到旧计划也不会白跑。
- 前端把引用翻成人话：「自动引用：第 2 步「检索文献」运行结果里的 results」——`$s2` 对用户是天书。

### 5.6 修「点了生成计划没下文」（2026-10-01 晚，用户报「生成之后不会回写」）

排查（看服务日志 + 任务文件）后确认：**不是回写的问题**，而是计划根本没生成成功。日志里连续出现
`POST /api/agent/plan → 409 Conflict`，同时在磁盘上留下了 **6 个永远停在 `planning` 的任务**。

根因在 `agent_plan` 的顺序：**先 `new_task()` 建记录，再 `_agent_bg()` 抢串行闸门**。
闸门被占时 409 抛出，但记录已经落盘 → 那个任务永远不会有人去执行它 → 前端一直转圈、用户以为"点了没反应"。

修法：
1. **先抢闸门 → 再建档 → 最后派活**（`_agent_acquire()` / `_agent_spawn()` 拆开）。
   抢不到就 409 且**不留任何记录**；409 文案里带上"是哪个任务在占着"，并提示可以中止它。
2. **回收卡死的任务**（`_reap_stale()`）：状态是 `planning`/`running` 但**没有执行线程**且已超过阈值
   （计划 10 分钟 / 执行 120 分钟）→ 标成 `failed` 并写明原因。挂在 `list_tasks()` 里，打开历史即自愈。
3. **计划阶段也给出口**：原先「中止」按钮在 `planning` 时是隐藏的，卡住就彻底没辙。现在计划阶段也显示「中止」，
   超过 150 秒还会提示"多半卡住了，点中止再重新生成"。另外 `plan_task` 会检查用户是否在等模型的
   那几十秒里点了中止——是的话直接丢弃这次结果，不再覆盖。
4. **能收拾残局**：终态（完成/失败/已中止）的任务卡片多一个「删除任务」；历史任务头多一个
   「清理失败/已中止（N）」，一键清掉残留。

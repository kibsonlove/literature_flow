# 智能体化改造调研

> 状态：调研稿（2026-10-01），未动手改任何代码。看完拍板后按第 5 节分阶段执行。

## 1. 结论摘要

这个工具离"智能体"**只差上面两层，底层能力已经很齐**：

- ✅ **能力层已有**：检索、入库、精读、语义检索、维护工具箱，模块化清晰，`/api/*` 路由即天然的工具调用面。
- ❌ **缺工具注册层**：能力散在各模块/路由里，没有统一的机器可读工具清单。
- ❌ **缺编排层**：按钮驱动的固定管线，没有 LLM 决策循环，没有对话入口。

**核心制约**：零 API 费的网页端通道（`webchat.run_webchat`）是一次性调用、每次开浏览器，**不适合逐步决策的紧循环**。因此推荐走"**粗粒度规划**"而非"逐步决策"——LLM 只在开头出一次计划、结尾出一次总结，中间执行交给确定性代码。

## 2. 现状盘点（已具备的）

### 2.1 能力清单（可直接工具化的）

| 能力 | 现有实现 | 副作用 |
|---|---|---|
| 文献检索（OpenAlex/arXiv） | `core/litsearch.py`，`/api/lit/search` | 无（只读） |
| 检索式生成 | `litsearch.generate_queries()`（网页端） | 无 |
| 结果入库 Zotero | `/api/lit/import` | **写库** |
| 批量精读/笔记 | `core/batch.py`、`longdoc.py`、`paperset.py` | 写笔记（幂等：已有笔记不重复生成） |
| 知识库语义检索 | `core/kb.py` `search()` | 无（`other_language_query` 走 API，刻意保留） |
| 条目检索/分类树 | `/api/zotero_search`、`/api/zotero_collections` 等 | 无（只读） |
| 分类归属（移动制） | zotero_io 写接口 | **写库** |
| 维护脚本（订阅/去重/标签） | `core/tools.py` 白名单运行器 | 变更类默认 dry-run |

### 2.2 LLM 通道

- 网页端 `WebChatTextSession` / `run_webchat(pdf, prompt)`：零费，但**一次性、需开浏览器、约 30 秒+/次**。
- API 备选（设置里配模型）：`domain_backend` 本机已显式锁定 `webchat`。

### 2.3 已有的安全资产（agent 化时直接继承）

- 写 Zotero 需授权（`zotero_io.write_authorized()`）；
- `tools.py` 变更类脚本默认 dry-run + 前端 confirm；
- 精读幂等（有笔记不重复生成）；查重（DOI+标题指纹）自动跳过已入库。

## 3. 差距：智能体还缺什么

### 3.1 工具注册层（必要）

一个统一登记处（建议 `core/agent_tools.py`），每个工具声明：

```
name / description / 参数 schema / 只读还是写库 / 返回摘要方式
```

写库工具必须标 `danger=True`。这份清单同时喂给规划 prompt 和前端确认 UI，一处维护两处生效。现有 `tools.py` 的 TOOLS 字典就是现成范本。

### 3.2 编排层（必要，但形态取决于 webchat 制约）

三种可选形态：

| 形态 | LLM 调用次数/任务 | 速度 | 智能程度 |
|---|---|---|---|
| A. 粗粒度规划（推荐）：开头一次出计划（JSON 步骤列表），代码逐步执行，结束一次总结 | 2 次 | 快 | 中——计划错了中途不自纠 |
| B. 逐步决策循环：每步问 LLM 下一步 | 5-10+ 次 | 慢（每步 30s+ 浏览器开销） | 高 |
| C. 混合：计划一次，仅在**失败/异常**时回头问 LLM | 2-4 次 | 较快 | 中高 |

推荐 **C**：正常路径零额外开销，出错才付 LLM 成本。

### 3.3 对话入口与任务状态

- 前端加一个「智能体」面板：自然语言输入框 + 计划展示（步骤列表，写库步骤高亮）+ 执行日志流。
- 后端任务状态落 `webapp/cache/`（可再生的运行态，不碰库），支持中断续跑、步骤跳过。

### 3.4 人工闸口（不可妥协）

计划里凡 `danger=True` 的步骤，**必须暂停等用户点确认**才执行。这是现有"入库要 confirm、变更有 dry-run"约定在 agent 形态下的等价物——绝不允许 agent 静默改 Zotero 库。

## 4. 路线对比

| 路线 | 改造量 | 优点 | 缺点 |
|---|---|---|---|
| **自建智能体模式**（推荐） | 中 | 体验完整、零 API 费、完全掌控安全边界 | 编排循环自己写（但推荐形态 C 很薄，核心逻辑约几百行） |
| 暴露成 MCP server | 小 | 不用自建对话循环，WorkBuddy 等现成 agent 直接调 | 依赖外部 agent 客户端；写库闸口交给外部 agent，风险不可控 |
| LangGraph 等框架重构 | 大 | 标准化 | 推翻稳定管线、依赖重、与 webchat 通道不兼容（框架默认按 API 设计），不推荐 |

两条路线不互斥：先做自建（主线），工具注册表做好后，包一层 MCP 只是薄壳，随时可加。

## 5. 推荐路线：分阶段方案

### P0 工具注册表（地基，半天量级）
- 新建 `core/agent_tools.py`：登记上表 8 类能力，标注只读/写库。
- 纯新增文件，不动现有模块，零风险。

### P1 计划-执行编排（核心，1-2 天量级）
- `core/agent_orchestrator.py`：输入自然语言任务 → webchat 出一次计划（JSON 步骤）→ 逐步执行（只读步骤直接跑，写库步骤等确认）→ 失败时才回问 LLM → 结束总结。
- 新增 `/api/agent/plan|confirm|status` 三个路由。
- **测试红线**：只读任务可实测；含写库的任务用小样 + 用户当场同意可整个删除的测试分类。

### P2 对话面板与体验（1 天量级）
- 前端「智能体」面板：输入 → 计划卡片（危险步骤红色高亮，沿用 `.danger`）→ 逐步日志 → 总结。
- 任务历史与中断续跑。

### P3（可选）MCP 薄壳
- 基于同一个注册表包 MCP server，供外部 agent 使用。

## 6. 硬约束（执行时不可违背）

1. LLM 调用默认走网页端 webchat；不引入按次计费 API 依赖。
2. 写库动作必须人工确认，agent 无静默写权限；变更类默认 dry-run。
3. 绝不拿真实文献做端到端测试。
4. 一切通用化，领域内容只作数据；路径走 `config` 函数，禁硬编码。
5. webchat 的浏览器 profile / 临时产物用完即清。

## 7. 开放问题（拍板前想清楚）

1. 计划的"中途回炉"要不要做？P1 先只做失败回问，够用就不加。
2. 精读是否纳入 agent 可调度的范围？批量精读耗时长、占浏览器，建议 P1 先不纳入，P2 再放开（每次任务限一个批量精读）。
3. 多任务并行还是串行？webchat 开的是同一个浏览器 profile，**只能串行**——这是硬限制，界面文案要写明。
